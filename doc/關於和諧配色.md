依據 W3C（CSS 工作小組）標準與現代色彩科學（Color Science），在網頁中計算 **和諧色彩（Color Harmony，如補色、三角色、四方色等）** 的演算法與工具原理，可以從「現代 CSS 最佳做法」與「Adobe 等工具的背後邏輯」兩個面向來解析：

---

### 一、 產生和諧色彩的最佳做法（色彩空間與演算法）

#### 1. 最佳色彩空間首選：`OKLCH`

在現代 CSS 中，產生幾何和諧色盤（如四方色：$0^\circ, 90^\circ, 180^\circ, 270^\circ$）的最佳做法是**在 `OKLCH` 色彩空間中進行極座標角度運算**。

- **為什麼不能用傳統的 HSL / HSV？（明度陷阱）**
  - 在 HSL 中，雖然可以輕易用數學做 `(hue + 90) % 360`，但 HSL **不具備感知均勻性**。
  - 若你的主色是純黃色（$60^\circ$），其互補色是純藍色（$240^\circ$）；在 HSL 裡兩者明度都是 $50\%$，但肉眼看黃色極亮、藍色極暗。算出來的四方色在視覺份量、文字可讀性與對比度上會完全崩潰。
- **OKLCH 的優勢**：
  - **明度（L）與彩度（C）絕對恆定**：旋轉色相角度 $H$ 時，四個顏色的視覺明度與強弱完全一致，不會產生某個顏色特別刺眼或某個顏色特別暗的情況。

#### 2. 現代 CSS 實作四方色（Tetradic / Square）

利用 CSS Color Module Level 5 的 **相對色彩語法（Relative Color Syntax）**，可以直接用純 CSS 計算四方色：

```css
:root {
  /* 基準品牌色 */
  --brand: oklch(65% 0.18 200);

  /* 四方色：固定 L 與 C，色相每次旋轉 90 度 */
  --square-1: var(--brand);
  --square-2: oklch(from var(--brand) l c calc(h + 90));
  --square-3: oklch(from var(--brand) l c calc(h + 180));
  --square-4: oklch(from var(--brand) l c calc(h + 270));
}
```

### 二、 Adobe Color 等配色工具是「純邏輯計算」還是「獨特公式」？

**答案是：它並非單純的 $360^\circ$ RGB 旋轉，而是經過了「傳統藝術色環（RYB）的非線性幾何映射」。**

如果你在 Adobe Color 網頁上選擇「互補色」，選取紅色（RGB 色相 $0^\circ$），你會發現對面的互補色其 RGB 色相值大約落在 **$137^\circ$（偏綠）**，而不是數學上的 **$180^\circ$（青色 Cyan）**。

#### 1. 為什麼 Adobe 不用單純的 RGB 數學角度？

- **RGB 光學色環**：紅色的對面是**青色（Cyan）**，黃色對面是**藍色（Blue）**。這是物理光學加法色。
- **傳統藝術 RYB 色環（伊登色環 Itten Wheel）**：數百年來美術界習慣的調和色是**紅配綠（Red-Green）**、**黃配紫（Yellow-Purple）**、**藍配橙（Blue-Orange）**。

#### 2. Adobe 的底層計算機制

Adobe Color 的核心調色引擎採取的是 **RGB ↔ RYB 的非線性插值映射**：

1. 使用者在 UI 看到的是一個模擬傳統畫家色環的轉盤（以紅、黃、藍為主導軸）。
2. 工具在底層先將使用者的 RGB 顏色透過多項式或三線性插值（Trilinear Interpolation）轉換至 **RYB 空間**。
3. 在 RYB 空間中依據角度規則進行旋轉（例如互補色 $+180^\circ$、四方色 $+90^\circ$）。
4. 最後再把計算出的 RYB 座標**逆向轉回 RGB / HSB** 呈現給網頁。

這就是為什麼很多前端工程師用 `(hue + 180) % 360` 寫出來的互補色，看起來跟 Adobe 算出來的「長得不一樣」。

| **插畫、視覺藝術、品牌行銷氛圍**                              | **RYB 映射演算法**（如 Adobe Color） | 遵循傳統美學經驗（紅綠、藍橙對比），視覺感受較為濃郁且符合直覺美感。 |

## 🟨Q：RYB 空間會有髒色、亮度不均勻的問題嗎？

🟩A：**會，而且非常嚴重。**

事實上， **「亮度不均勻」** 與 **「混色容易發灰發髒」** 正是傳統 RYB（紅黃藍）模型在現代色彩科學與數位 UI 設計中面臨的兩大核心缺陷。

---

### 一、 為什麼 RYB 會有「亮度極不均勻」的問題？

RYB 是一個基於歷史經驗與美術直覺的「色相環（Hue Wheel）」，**它完全沒有獨立的「感知明度（Perceptual Lightness）」維度**。

1. **天然的明度極端差**：
   - 在 RYB 色環上， **黃色（Yellow）** 天生具有極高的光學明度，而對面的 **紫色（Purple）** 或旁邊的 **藍色（Blue）** 天生非常暗。
2. **和諧色旋轉時的明度崩潰**：
   - 當你在 RYB 色環上做等角旋轉（例如互補色 $180^\circ$ 或四方色 $90^\circ$）時，產生的顏色**明度會劇烈跳動**。
   - **結果**：如果直接把 RYB 算出來的四方色套用在網頁排版中，黃色文字會亮到看不清、藍色/紫色文字會暗到沉下去，**完全無法保證無障礙（WCAG）對比度的一致性**。

---

### 二、 為什麼 RYB 在數位計算中容易出現「髒色」？

「髒色（Muddy Colors）」主要是指**在漸層過渡或顏色混合時，中間色調出現非預期的發灰、彩度驟降或渾濁感**：

1. **模擬減法混色的天生副作用**：
   - RYB 的本質是模擬「實體顏料（減法混色）」。當你把兩個互補或色相較遠的顏色在 RYB 中混合時，它會模擬顏料吸收光線的過程，中間過渡會迅速朝 **暗濁的棕灰色（Muddy Brown/Gray）** 塌陷。
2. **數位插值（Interpolation）的數學失真**：
   - 電腦在處理 RYB 時，通常是用數學演算法（如 Gossett & Chen 提出的三線性插值）在 RGB 與 RYB 之間硬轉。這種非線性變形會造成**彩度（Chroma）在某些色相過渡區間被大幅壓縮**，導致漸層中間出現明顯黯淡無光的「灰色死區」。

---

### 三、 既然缺陷這麼多，為什麼 Adobe 等工具還要用 RYB？

既然 RYB 又髒、亮度又不均勻，為什麼設計界不直接拋棄它？

- **文化與心理習慣（Psychological Expectation）**：
  百年來的美術教育（如包浩斯的伊登色環、歌德色彩論）讓人類大腦建立了深刻的文化制約——我們習慣認為「紅配綠」、「藍配橙」、「黃配紫」是和諧的對比。
- **Adobe 的妥協做法**：
  Adobe Color 這類工具**只藉助 RYB 來決定「色相（Hue）」的角度關係**，但顏色的「明度與飽和度」則額外留給設計師手動微調，或者靠後續演算法去補償。它犧牲了數學上的均勻性，換取了符合大眾視覺經驗的「藝術和諧感」。

---

### 四、 現代色彩科學的解決方案

針對這兩個問題，現代技術已經發展出更好的替代方案：

| 需求場景                          | 傳統 RYB 的問題            | 現代最佳解法                                      | 原理與效果                                                                             |
| :-------------------------------- | :------------------------- | :------------------------------------------------ | :------------------------------------------------------------------------------------- |
| **網頁 UI、設計系統、無障礙排版** | 明度忽高忽低、對比度不可控 | **`OKLCH`**                                       | 嚴格鎖定感知明度（L），旋轉色相時**明度絕對均勻**，排版永遠不破壞對比度。              |
| **數位繪畫、模擬真實顏料混色**    | 數學插值過渡發髒、發灰     | **Kubelka-Munk 光譜混色**（例如 _Mixbox_ 演算法） | 透過光學反射率與顏料散射物理公式計算，讓藍加黃能真正過渡出**鮮豔的綠色**，而非髒灰色。 |

### 總結

- **RYB** 是 **「藝術文化導向」** 的模型：擅長提供直覺的色相對比，但存在**髒色與明度不均**的硬傷。
- **OKLCH** 是 **「人類視覺科學導向」** 的模型：徹底解決了髒色與明度不均，是當前**網頁工程與設計系統的最佳標準**。

## 🟨Q：RYB的色相關係，例如「紅配綠」、「藍配橙」、「黃配紫」等等，在OKLCH中是否也會是相同角度關係？

🟩A：**不是，它們的角度關係完全不同。**

如果在 OKLCH 中將色相旋轉 $180^\circ$（幾何對角），你得到的互補色會與傳統美術的 RYB 色環有巨大差異。

---

### 一、 核心差異對照表（$180^\circ$ 互補色對比）

| 基準色            | 傳統 RYB 色環的互補色（$180^\circ$） | **OKLCH 中的真實光學互補色（$180^\circ$）** |
| :---------------- | :----------------------------------- | :------------------------------------------ |
| **黃色 (Yellow)** | **紫色 (Purple)**                    | **藍色 (Blue)**                             |
| **藍色 (Blue)**   | **橙色 (Orange)**                    | **黃色 (Yellow)**                           |
| **紅色 (Red)**    | **綠色 (Green)**                     | **青綠色 / 水藍色 (Cyan / Teal)**           |

### 二、 為什麼兩者的角度會完全不一樣？

#### 1. OKLCH 的科學基礎：人眼的「對立色理論（Opponent Process Theory）」

OKLab / OKLCH 的座標軸是根據人類大腦神經處理色彩的生物生理機制建立的：

- **`a` 軸**：代表 **紅 — 綠（Red vs. Green）** 對立訊號。
- **`b` 軸**：代表 **黃 — 藍（Yellow vs. Blue）** 對立訊號。

這代表在人類視覺感知中：

- **黃色（約 $90^\circ$）的真正生物視覺對立面是「藍色（約 $270^\circ$）」**。
- **紅色（約 $25^\circ$）的真正生物視覺對立面是「青綠色（約 $205^\circ$）」**。

#### 2. RYB 是「歷史顏料調色經驗」，而非視覺生理

RYB 色環起源於數百年前畫家混合實體顏料（如鎘黃、群青、辰砂紅）的經驗。在顏料調色中，黃色加紫色可以調出中性灰褐色，因此畫家將它們視為「互補」；但在人類視覺神經的光學刺激中，黃色的互補刺激其實是藍色。

---

### 三、 這對網頁配色與寫 CSS 有什麼影響？

如果你想在 CSS 中使用傳統美術教育中的配色感受，你需要知道：**在 OKLCH 中不能單純用 `calc(h + 180)` 來求取 RYB 意義下的互補色。**

#### 1. 若使用 OKLCH 的幾何旋轉（數學上的 $180^\circ$）：

你會得到**光學與視覺感知上最強烈對比**的組合（例如：黃配藍、橙配天藍）。這在 UI 上非常適合用來做高對比醒目提示，且能確保文字與背景的明度可控。

```css
/* OKLCH 光學互補：藍色 配 黃色 */
--primary-blue: oklch(60% 0.2 260);
--accent-yellow: oklch(
  from var(--primary-blue) l c calc(h + 180)
); /* 260 + 180 = 80 (黃色) */
```

#### 2. 若想做出傳統美術的「藍配橙」或「黃配紫」：

在 OKLCH 中，這屬於 **「偏補色（Split-Complementary）」** 或非對稱的角度關係，角度差大約在 **$140^\circ \sim 150^\circ$** 左右，而非 $180^\circ$：

```css
/* 傳統藝術和諧：藍色 配 橙色（在 OKLCH 中大約旋轉 150 度而非 180 度） */
--primary-blue: oklch(60% 0.2 260);
--art-orange: oklch(
  from var(--primary-blue) l c calc(h - 150)
); /* 260 - 150 = 110... 大約在 50~60 度橙色區間 */
```

### 總結

- **OKLCH** 的 $180^\circ$ 是 **「黃配藍、紅配青綠」**（視覺生理的真實補色）。
- **RYB** 的 $180^\circ$ 是 **「黃配紫、藍配橙、紅配綠」**（傳統繪畫的經驗補色）。
- 兩者在色相環上的**幾何角度完全不相等**。

## 🟨Q：現代色彩科學有沒有研究哪種色彩空間的和諧色，最能讓人感覺舒服、好看？

🟩A：現代色彩心理學、視覺科學（Color Psychophysics）以及計算美學（Computational Aesthetics）對此有相當豐富且深入的量化研究。

科學界的明確共識是：**在「感知均勻的色彩外觀模型（如 CIECAM02/16、CIELAB、OKLab/OKLCH）」中計算出來的和諧色，最能符合人類視覺的「舒適感」與「美感」。**

以下是現代色彩科學在研究「什麼配色彩讓人舒服」時的關鍵發現與核心理論：

---

### 一、 權威的科學和諧量化模型：Ou & Luo 模型 (2006)

在現代色彩科學中，最著名且被廣泛驗證的是由色彩學權威 **Li-Chen Ou（歐立成）與 M. Ronnier Luo（羅明教授）** 提出的「雙色和諧量化模型（Ou-Luo Color Harmony Model）」。

研究團隊在 **CIECAM02** 與 **CIELAB** 等感知色彩空間中，對數千組色彩搭配進行了大規模的人類心理物理學實驗，發現**讓人類大腦覺得「和諧、舒服」的配色，滿足以下幾項數學規律**：

1. **明度差效應（Lightness Difference, $\Delta L$）**：
   - 舒服的配色通常具備**適度且清晰的明度差異**。如果兩種顏色的色相不同，但明度「極度接近卻又不完全相同」，會在大腦邊界神經產生視覺干擾與閃爍感（視覺疲勞）。
2. **彩度平衡效應（Chroma Effect, $\Delta C$）**：
   - 中低彩度（低飽和度）的色彩組合普遍比全高彩度的組合獲得更高的人類好感度評分。
   - 高彩度的顏色必須搭配低彩度的中性色，才能達到視覺放鬆的效果。
3. **同等知覺距離（Perceptual Uniformity）**：
   - 傳統 HSV/sRGB 的幾何等分在人類大腦看來是「扭曲的」；只有在 **CIECAM02、OKLCH** 這類感知均勻空間中，等角度旋轉所產生的色相跳躍才符合人類大腦神經的感知等距。

---

### 二、 生態效價理論（Ecological Valence Theory, EVT）

加州大學柏克萊分校的認知心理學家 **Stephen Palmer 與 Karen Schloss (2010)** 提出了著名的「生態效價理論」：

- 人類對特定顏色及顏色組合的好感，來自於**演化過程中對自然界事物的聯想**（例如：純淨的天空藍、清澈的水、成熟的果實令人愉悅；而混濁發霉的灰綠、腐敗的暗黃令人排斥）。
- **研究結論**：在均勻色彩空間（如 CIELAB/OKLCH）中漸層與混合時，因為**不會產生非預期的灰濁髒色（Muddy Colors）**，調配出來的顏色在生態聯想上更接近自然界的純淨物體，人類的潛意識接受度顯著更高。

---

### 三、 為什麼現代科學認為「OKLCH / CIECAM」算出來的最好看？

過去幾百年，古典理論（如伊登、歌德、孟塞爾）認為「只要色環角度對了（如 $180^\circ$ 互補、$120^\circ$ 三角色），顏色就會好看」。

但現代色彩科學發現：**決定配色舒不舒服的關鍵，70% 取決於「明度（L）與彩度（C）的配置關係」，色相（H）角度只佔 30%。**

| 色彩空間           | 計算和諧色時的表現                                     | 人類主觀感受                                                           |
| :----------------- | :----------------------------------------------------- | :--------------------------------------------------------------------- |
| **HSV / HSL**      | 轉動色相時，明度與彩度劇烈失真。                       | 容易出現刺眼對比或某色過於強烈，**容易視覺疲勞**。                     |
| **RYB (藝術色環)** | 偏向文化直覺（紅綠、藍橙），但明度跳動劇烈。           | 具備傳統藝術美感，但**容易髒色、介面閱讀對比不易控制**。               |
| **OKLCH / CAM16**  | **明度與彩度完全受控**，色相幾何旋轉符合大腦知覺等距。 | **最舒適、協調**。文字可讀性極佳，畫面視覺重量平衡，不易造成視覺疲憊。 |

---

### 四、 科學建議的「舒服配色」黃金法則

如果你想利用現代色彩學（特別是使用 `oklch`）做出讓人最舒服的配色，科學研究推薦以下配置法：

1. **同調配色（Monochromatic / Iso-chroma）**：
   - 固定色相 $H$，調配不同的明度 $L$ 與微調彩度 $C$。大腦處理這種色彩組合的神經負擔最低，被公認是**最不易疲勞、最優雅**的配色。
2. **類比和諧色（Analogous，OKLCH 角度差約 $30^\circ \sim 40^\circ$）**：
   - 挑選色相相近的顏色，維持相同的明度 $L$，微幅降低副色的彩度 $C$。在自然界極為常見（如樹葉與花卉的漸變）。
3. **互補/強調色（Accent Contrast）**：
   - 主背景與主色保持低彩度（例如 $C < 0.05$），僅在需要吸引注意力的強調色（Accent）上使用高彩度（$C > 0.15$），大腦會給予最高的審美評價。

## 🟨Q：目前，提供整套配色方案的工具中，例如google m3等等，是否有依循這些色彩科學研究成果的？

🟩A：**有的，而且目前全球頂尖的設計系統與配色工具，已經全面揚棄傳統的 RGB/HSL 色環，轉向以「現代色彩科學模型」為核心來建構整套配色方案。**

以下為目前業界最具代表性、嚴格依循色彩科學研究成果的系統與工具：

---

### 1. Google Material Design 3 (Material You) —— **HCT 色彩空間**

Google 在推出 Material Design 3 (M3) 的「動態色彩（Dynamic Color）」時，發現傳統的色彩模型（RGB、HSL、CIELAB）均無法滿足演算法自動配色的需求，因此專門研發了一套全新的色彩空間：**HCT（Hue, Chroma, Tone）**。

- **底層色彩科學架構**：
  - **H（Hue 色相）與 C（Chroma 彩度）**：採用 **CAM16**（現代色彩外觀模型，能精準模擬人眼在不同環境光源下的色彩適應機制）。
  - **T（Tone 感知明度）**：採用 **CIE $L^*$**（與光學對比度、人類亮度感知完全線性對齊）。
- **科學配色運作方式**：
  - 當使用者上傳一張桌布，系統提取出一個主色（Seed Color）。
  - 演算法不是直接算旋轉角度，而是將其映射進 CAM16 空間，依據 **感知明度（Tone）階梯（0 到 100）** 自動生成 5 種調和色群（Primary, Secondary, Tertiary, Neutral, Neutral Variant）。
  - **成果**：無論算出來是什麼顏色，**在 Tone = 40 與 Tone = 90 之間的文字與背景，永遠數學保證符合 WCAG 4.5:1 的無障礙對比度**，徹底解決了黃色太亮、藍色太暗導致介面看不清的問題。

---

### 2. Adobe Leonardo (leonardocolor.io) —— **自適應對比度色彩系統**

由 Adobe 的設計團隊主導開源的 **Leonardo**，是專門為現代設計系統（Design Systems）打造的色彩工具，它完全拋棄了傳統「手動選 10 個色階」的做法。

- **底層色彩科學架構**：
  - 支援 **OKLab、CIELAB、CAM02**。
  - 採用 **APCA（進階感知對比度演算法，未來的 WCAG 3 標準）**。
- **科學配色運作方式**：
  - 設計師輸入的不是「具體色值」，而是輸入 **「目標對比度（Contrast Ratio）」**（例如：按鈕需要對比度 4.5，懸停需要 3.0）。
  - 系統利用 OKLab/CIELAB 的感知均勻性，**反向計算**出符合該對比度的精準色彩。
  - **成果**：當你把品牌主色從藍色切換成黃色時，整個介面的可讀性與對比階梯完全不會跑版。

---

### 3. Tailwind CSS v4 —— **全面轉向 OKLCH**

作為全球最普及的前端 CSS 框架，Tailwind CSS 自 **v4.0** 開始，將其預設的整套調色盤（包含 Slate, Red, Amber, Emerald, Blue 等所有 50~950 色階）**全部重構為 `oklch()`**。

- **解決的痛點**：
  - 舊版使用 sRGB/Hex 時，不同顏色的相同色階（例如 `blue-500` 和 `yellow-500`）在視覺亮度和對比度上極不一致。
  - 改用 **OKLCH** 後，所有色系的色階明度曲線完全平滑對齊，並且在 Apple Display P3 等廣色域螢幕上能自動釋放出更鮮豔、更高飽和度的色彩，而不會產生發髒的失真。

---

### 4. Stripe 的色彩系統（Stripe Color System）

支付巨頭 Stripe 的介面配色被業界視為頂級典範。Stripe 曾發表過長篇色彩工程技術報告，分享他們如何利用色彩科學重構全站配色：

- **科學做法**：
  - 他們發現使用傳統 HSL 做出的 12 種品牌色，在無障礙標準下有近一半是不合格的。
  - Stripe 團隊導入 **CIELAB / LCH 空間**，寫了一套演算法重新校準所有顏色的感知明度（Perceptual Lightness），讓同一階（如 Level 40）的黃色、藍色、綠色在視覺重量上完全等重。

---

### 💡 現代權威配色工具的「三大共同科學原則」

現在業界採用的配色工具，幾乎都遵循以下三大現代色彩學共識：

1. **明度（Tone / Lightness）與色相徹底解耦**：
   決定介面層次與可讀性的是「感知明度」，不再依賴 RGB/HSL 的非線性數值。
2. **無障礙對比度（APCA / WCAG）優先於幾何角度**：
   不再死板地旋轉 $180^\circ$ 或 $90^\circ$，而是以「明度階差（$\Delta L$）」與「適當的彩度（Chroma）」作為和諧與可讀性的第一考量。
3. **全面導入 Perceptual Color Spaces**：
   Google 使用 **HCT (CAM16 + $L^*$)**，網頁與 CSS 標準使用 **OKLCH / OKLab**，徹底消除了數位漸層發灰與髒色的問題。

## 🟨Q：

我曾實際用HCT製作過四方色等和諧色，也曾用M3來配色。
直覺上第一印象會覺得M3的配色偏向鮮豔，適合做鮮明的UI，但你如果希望頁面整體帶柔和感的話，不容易達成。
HCT產生的和諧色，會給人一種「不是常見的和諧色關係」的印象，會懷疑是否算錯了。從"和諧、協調"的觀感來說，Adobe Color 的第一印象還是比較好。
這部分不知道有沒相關的研究報告。

🟩A：你的這個觀察**非常敏銳，且完全切中了當代色彩科學與 UI 設計實務交會處的最大爭議點**。

在設計界與色彩認知心理學中，確實有非常多針對這個現象的研究、實測報告與業界探討。你感受到的「**M3 太過鮮豔/難做柔和色**」以及「**HCT 和諧色看起來怪怪的、不像傳統和諧色**」，背後有非常具體的**演算法機制**與**心理認知原理**：

---

### 一、 為什麼 M3 很難做出柔和感？（演算法強制拉高彩度）

許多設計師在 Medium、Figma 社群與技術論壇中都抱怨過：「我給 M3 一個低飽和的莫蘭迪色或柔和灰粉色，算出來的介面卻還是像糖果色一樣鮮豔。」

#### 1. Google 演算法的「最低彩度鉗制（Chroma Clamping）」

Google M3 的核心目標是 **Android 手機在戶外強光下的「可讀性」與「功能無障礙（WCAG）」**。

- 在 `material-color-utilities` 的原始碼中，為了確保按鈕與背景在任何螢幕上都能被一眼認出，演算法**設定了彩度下限**。
- 如果你輸入一個極低彩度（$C < 16$）的柔和種子色，演算法會 **強制將 Primary 與 Tertiary 的彩度「補償/放大」** 到一定的數值。

#### 2. M3 預設主題演算法（`SchemeTonalSpot`）的強制偏色

M3 預設使用的不是「原汁原味」保留你選的顏色，而是名為 **Tonal Spot** 的演算法：

- 它會把你的主色稍微降彩度，但**強制將「第三色（Tertiary）」的色相旋轉約 $+60^\circ$ 並拉高彩度**，企圖創造活潑的視覺焦點。
- 這導致如果你想做一個整體都是低飽和灰調、日系無印風或極簡柔和感的頁面，M3 會「自作聰明」地插進一個鮮豔的對比色破壞整體氛圍。

> **補充**：Google 後續收到了大量專業設計師的反饋，才在演算法中追加了 `SchemeFidelity`（忠實還原種子色）與 `SchemeContent`、`SchemeNeutral` 等不同風格變體，允許設計師關閉這種強制的鮮豔度。

---

### 二、 為什麼 HCT 的和諧色讓人覺得「怪怪的、不像和諧色」？

這牽涉到色彩認知心理學中 **「生物生理光學（HCT/CAM16）」** 與 **「文化美學記憶（Adobe Color/RYB）」** 的衝突。

#### 1. 文化制約與大腦的「和諧記憶」

加州大學柏克萊分校的 **Karen Schloss 與 Stephen Palmer (2011)** 在《Aesthetic response to color combinations: preference, harmony, and similarity》研究中指出：

- **人類感受到的「和諧感（Harmony）」很大程度建立在「文化熟悉度（Familiarity）」上。**
- 幾百年來，人類所有的繪畫、攝影、電影調色、甚至是小學美術教育，全部都是建立在 **伊登色環（RYB）** 上（例如：溫暖的藍配橙、復古的紅配綠、高貴的黃配紫）。
- **Adobe Color** 背後的邏輯就是映射這種傳統藝術色環。當你看到 Adobe 配出的藍配橙時，你的大腦會立刻喚起對「日落大海」、「電影調色（Teal & Orange）」的熟悉美感，第一印象自然極好。

#### 2. HCT 的旋轉是「視神經物理對立」，而非「藝術聯想」

HCT（基於 CAM16）是完全按照人類視網膜上的錐狀細胞與大腦皮質的電訊號來計算的：

- 在 HCT 中旋轉 $180^\circ$，**藍色對面是「黃色」**，**紅色對面是「青水綠色」**。
- 當你用 HCT 算四方色（$90^\circ$ 等分）時，它算出來的是「神經感知訊號等距」，但這個組合在傳統藝術中幾乎很少以純色同時出現。
- 這會讓習慣了傳統藝術配色的眼睛產生 **「認知失調（Cognitive Dissonance）」** ——你的大腦會覺得：「這四個顏色在生理上確實明度一樣、份量一樣，但湊在一起怎麼不像我平常看習慣的名畫或經典設計？」

---

### 三、 相關研究與測試結論：生理可讀性 $\neq$ 審美愉悅度

現代色彩科學的研究報告（如歐立成教授與英國里茲大學色彩小組的研究）得出了一個重要分野：

1. **HCT / OKLCH 的強項在於「功能性（Functional Performance）」**：
   - 在需要**嚴格無障礙、資訊圖表、複雜狀態提示、跨光源辨識**的場景下，HCT 算出的顏色是無懈可擊的，因為它的明度差與對比度在數學上是完美的。
2. **傳統藝術色環（Adobe Color 等）的強項在於「情感與審美（Aesthetic & Emotional Preference）」**：
   - 在需要營造**品牌氛圍、柔和調性、藝術感、插畫風格**時，人類的情感偏好依然高度偏向經過歷史沉澱的「非對稱、帶有藝術經驗微調」的和諧關係。

---

### 💡 實務上的解決建議

如果你喜歡 **HCT / OKLCH 帶來的精準明度控制**，但又想要 **Adobe Color 那種柔和、符合直覺的和諧感**：

1. **手動指定色相（Hue），只用 OKLCH / HCT 算明度與彩度**：
   - **不要依賴演算法自動旋轉 $90^\circ$ 或 $180^\circ$**。
   - 按照你的審美（例如用 Adobe Color 挑選出你喜歡的色相角度，如 $H_1=250^\circ, H_2=50^\circ$），然後**將這些色相帶入 `oklch` 中**，統一指定低彩度（如 `c: 0.04 ~ 0.08`）與受控的明度。
2. **在 M3 中避開 `SchemeTonalSpot`**：
   - 若使用 Google 的開源套件，改用 `SchemeFidelity` 或 `SchemeNeutral` 模式，它就不會強制拉高飽和度，能順利產出莫蘭迪色系與柔和粉彩調。

## 🟨Q：

我用 adobe color 選了一組偏亮的四方色： #FAFC79 #FCA379 #BB79FC #79FCEF
然後利用HCT計算，以 #FAFC79 為基準色(HCT: 112.056, 50.846, 96.541)，保持各色的hue值，而將C及T對齊基準色。
這時候會看到第二、第三個顏色明顯變得彩度很低，第四個顏色彩度稍好些，但也沒有基準色的彩度高。
這與預期不相符，因為C值既然相同(50.846)會期望視覺上是接近相同感受的。
實測上發現，第二、第三個顏色必須將T值降低一些，大約92，彩度才會與基準色接近。 這是什麼原因？

🟩A：這是一個非常經典且教科書等級的 **「色彩立體空間與螢幕色域截斷（Gamut Clamping）」** 現象。

簡單說一句結論：**不是 HCT 算錯了，而是你指定的顏色在 $T = 96.541$ 的極高明度下，在螢幕的物理極限（sRGB 色域）中「根本不存在」，HCT 為了不破圖，在背後偷偷強制把彩度（C）閹割調低了。**

以下為你詳細拆解背後的原因：

---

### 一、 核心原因：色彩立體的「圓錐極限（Gamut Boundary）」

螢幕顯示的所有顏色，在 3D 空間中並非一個規律的圓柱體，而是一個**凹凸不平的雙錐體（Color Solid）**：

- 頂點（$T = 100$）是純白 `#FFFFFF`（彩度 $C = 0$）。
- 底點（$T = 0$）是純黑 `#000000`（彩度 $C = 0$）。
- 越靠近頂部（$T > 90$），立體空間會**急速向內收縮成一個極小的尖點**，代表所有顏色在接近純白時，允許存在的最大彩度（Max Chroma）都會雪崩式下降。

---

### 二、 為什麼黃色做得到，紫色和橙色做不到？

不同色相（Hue）在光學與物理上有完全不同的「最大彩度峰值（Peak Chroma）」：

```
明度 (T)
100 ┼                  純白頂點 (C=0)
    │                /
 96 ┼───────[黃色峰值 (C≈50)]───[紫色/橙色已被嚴重截斷 (C只能到 10~15)]
 90 ┼             /              \
    │            /                \
 60 ┼──[橙色峰值 (C≈80)]           \
    │                               \
 40 ┼───────────────[紫色峰值 (C≈90)]
    │                               /
  0 ┼                  純黑底點 (C=0)
    └───────────────────────────────────── 彩度 (C)
```

1. **基準色黃綠色（#FAFC79，H=112）的天生優勢**：
   - 黃色與黃綠色在光學上是紅光與綠光的疊加，它天生就**聚集在極高明度區**（$T \approx 90 \sim 97$）。因此在 $T = 96.541$ 時，黃綠色依然能輕鬆達到 $C = 50.846$ 的高彩度。
2. **紫色（#BB79FC）與橙色（#FCA379）的物理悲劇**：
   - **紫色**是天生的「暗色系」，它最鮮豔的狀態出現在 **$T \approx 30 \sim 50$**；
   - **橙色**最鮮豔的狀態出現在 **$T \approx 55 \sim 65$**。
   - 當你硬把紫色和橙色拉到 $T = 96.541$（極度接近純白）時，在 sRGB 色域中，紫色允許的最大彩度可能只剩下 **$C \approx 12$**，橙色可能只剩 **$C \approx 18$**。

---

### 三、 HCT 在背後做了什麼事？

當你要求 HCT 產生：
`HCT(Hue = 紫色, Chroma = 50.846, Tone = 96.541)`

因為這個顏色已經**遠遠超出了螢幕色域（Out-of-Gamut）**，HCT 演算法的處理原則是：

> **「優先保證 Tone（明度）絕對正確，犧牲 Chroma（彩度）進行截斷。」**

因此，HCT 輸出的 RGB 色碼，其**實際真實的彩度其實已經被強制降到了 10 幾**。這就是為什麼你看到的第二、第三個顏色會「明顯變得彩度很低、像被洗白一樣」。

---

### 四、 為什麼你把 T 降到 92 之後，彩度就恢復了？

你的實測**完全驗證了色彩科學的幾何原理**：

- 當明度從 $T = 96.541$ 降到 $T = 92$ 時，你從色彩立體的最頂端尖錐稍微往下降了一點，**色彩空間的體積迅速擴大**。
- 在 $T = 92$ 時，sRGB 允許紫色和橙色達到的最大彩度顯著提高（可以容納 $C \approx 40 \sim 50$ 了），HCT 就不需要對彩度進行那麼嚴厲的閹割，所以它們的視覺飽和度瞬間就跟黃綠色追平了。

---

### 💡 實務結論與調色建議

1. **不要用「黃色的極限明度」作為全套配色的基準 Tone**：
   黃色是色彩界的「特例」，只有它能在 $T=96$ 時維持鮮豔。如果你希望整套四方色在維持「相同 T」與「相同 C」的前提下都鮮明好看，基準 Tone 必須降到大家的**交集安全區（通常在 $T \approx 75 \sim 85$）**。
2. **順應「自然明度順序（Natural Lightness Order）」**：
   在大自然與人眼審美中，**「本來就不該強求所有顏色都在同一個 Tone」**。
   - 黃色天生就該亮（$T=90 \sim 96$）
   - 橙色居中（$T=70 \sim 80$）
   - 紫色/藍色天生就該偏深（$T=50 \sim 65$）

   順應這個自然明度分佈去配置顏色，既不會觸發色域截斷（色彩不會褪色變髒），在大腦看來也是最舒適、最自然的配色。

---

## 🟨Q：應該在選完adobe color之後，保持H值，將T固定為80或50(中間)，然後讓其他顏色的C與基準色對齊。這樣生成色階時就不會超出範圍，對嗎？

🟩A：**你的大方向完全正確！這樣做可以大幅解決「某一色突然褪色、嚴重發白」的問題。**

但有一個**關鍵限制**需要注意：**基準彩度（$C$ 值）不能抓得太高**，否則在某些色相上依然會踢到色域鐵板。

以下為你詳細說明為什麼這樣做有效，以及實務操作時的最佳安全數值：

---

### 一、 為什麼把 T 固定在中間調（如 T=50～70）有效？

因為在色彩立體空間中，**中間調（$T \approx 50 \sim 70$）是所有色相（紅、橙、黃、綠、藍、紫）色域空間「交集最大、容忍度最高」的區域**。

- 避開了 $T > 90$ 的「純白頂點尖錐區」（紫色、橙色會被截斷）。
- 避開了 $T < 20$ 的「純黑底點尖錐區」（黃色、青色會被截斷）。

當你在中間調採樣時，各個色相都有足夠的物理空間去承載合理的彩度。

---

### 二、 唯一需要小心的陷阱：「木桶理論（最低彩度上限）」

雖然把 $T$ 定在中間調，但**如果你抓的 $C$ 值過高，依然會破功**。

- **舉例**：
  如果你的基準色是極其濃郁的翠綠色或天藍色，其彩度高達 **$C = 80$**：
  - 當你強迫黃色在 $T = 50$ 時也要達到 $C = 80$ 時，**黃色會先崩潰**（因為黃色在 $T=50$ 的暗部是橄欖褐/暗黃色，在 sRGB 中根本做不到 $C=80$，上限可能只有 $C \approx 45$）。
  - 同樣地，青水綠色（Teal）在 $T=50$ 時也很難達到 $C=80$。

#### 💡 解決法則：選擇「安全的黃金 C 值」

如果你希望 4 個顏色設定**相同的 $C$**，且在中間調完全不觸發破圖截斷，請依據你的設計風格將 $C$ 控制在以下安全區間：

| 設計風格                    | 建議統一的 Chroma ($C$) | 說明                                                                           |
| :-------------------------- | :---------------------- | :----------------------------------------------------------------------------- |
| **柔和莫蘭迪風 / 日系粉彩** | **$C = 12 \sim 22$**    | 絕對安全，全色相在 $T=30 \sim 90$ 均不會被截斷，呈現溫和高級感。               |
| **標準現代 UI / 商業軟體**  | **$C = 28 \sim 42$**    | **最推薦的黃金區間**。視覺飽和度適中，四方色彼此平衡且全在安全色域內。         |
| **鮮豔鮮明風 / 活潑主題**   | **$C = 45 \sim 55$**    | 接近 sRGB 某些色相（如黃色中調、青色中調）的極限邊界，需實測各色是否微幅偏色。 |

---

### 三、 產生整條色階（T=0～100）時的正確心態

當你用一組 `(Hue, 統一的 C)` 去生成整條色階時，請記住：

1. **在 $T=95$（極淺底色）或 $T=10$（極深文字色）時，顏色被截斷是「完全正常且必要的」**：
   - 在 $T=95$ 時，紫色自動降到 $C \approx 10$、黃色降到 $C \approx 20$，這是正確的！因為這個色階本來就是拿來當「極淡的卡片背景（Surface Container）」，它本來就不該太濃。
2. **只要關鍵使用區（$T=40 \sim 80$，主要按鈕、強調標籤、圖表）的彩度一致**，整套 UI 在肉眼看來就會具備極高的秩序感與一致性。

---

### 四、 最推薦的標準調色流程（SOP）

你可以把你的生成流程標準化為以下 4 步：

1. **選色相**：在 Adobe Color 挑選你覺得和諧好看的 4 個色相角度（$H_1, H_2, H_3, H_4$）。
2. **定彩度**：不要直接複製 Adobe 上某個極端顏色的 $C$，而是根據風格**直接指定一個統一的 $C$ 值**（例如：一般 UI 設 `C = 36`）。
3. **產色階**：將 4 組 `(H_n, C = 36)` 分別送進 HCT 色階生成器，產出 4 條 Tonal Palettes（$T = 10, 20, \dots, 90, 95$）。
4. **驗收配對**：
   - 按鈕主色取 $T = 40$（淺色模式）或 $T = 80$（深色模式）。
   - 容器底色取 $T = 90$ 或 $95$。
   - 文字取 $T = 10$。

**結論**：依照你構想的這個流程，只要 **$C$ 值不抓在極端超高值（維持在 40 左右或更低）**，整套四方色色階就能完美運作，既享有 Adobe 的藝術和諧色相關係，又享有 HCT 的精準無障礙對比與色彩平衡！

## 🟨Q：使用 HCT 與 oklch 產生顏色的色階表，會有什麼不同？

🟩A：使用 **HCT**（Google Material 3 核心）與 **OKLCH**（W3C CSS 現代標準）來生成一整套色階表（例如 10～90 或 50～950 的階梯色票），兩者在 **「底層哲學」、「對比度預測性」、「彩度曲線處理」** 以及 **「CSS 實作便利性」** 上有著非常具體的差異。

---

### 一、 核心架構與對比度預測的差異

| 比較維度           | **HCT 色階表 (Material 3)**                                                                               | **OKLCH 色階表 (CSS 現代標準)**                                                                                  |
| :----------------- | :-------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| **明度核心依據**   | **Tone ($T$) = CIE $L^*$**                                                                                | **Lightness ($L$) = OKLab $L$**                                                                                  |
| **設計初衷**       | 專為**嚴格通過現行 WCAG 2.1 對比度**而生                                                                  | 專為**現代人類視覺感知均勻性（Perceptual Uniformity）**而生                                                      |
| **對比度預測能力** | **「數學公式上的絕對保證」**<br>任意兩色的 $\Delta T \ge 50$，就**必定達到 WCAG 4.5:1**，不管色相是什麼。 | **「肉眼視覺上的絕對均勻」**<br>相同 $L$ 值的顏色在肉眼看來亮度絕對相同，更契合未來的 **APCA (WCAG 3)** 演算法。 |

- **實際感受差異**：
  - **HCT** 的色階是「功能導向」的。你在淺色模式挑 $T=40$ 當按鈕、$T=90$ 當底色，或者暗色模式挑 $T=80$ 當按鈕、$T=20$ 當底色，**程式碼完全不用重新驗算，對比度保證 100% 達標**。
  - **OKLCH** 的色階是「美學與感知導向」的。不同色相在相同 $L$ 值下，視覺份量最為平衡；但若換算回舊時代的 WCAG 2.1 數學公式時（因舊公式對藍色和黃色有缺陷），偶爾會出現極微小的對比度數值浮動。

---

### 二、 色域邊界與彩度（Chroma）的處理方式

當明度走向極端（例如極淺色 $T/L > 90$ 或極深色 $T/L < 20$）時，兩者生成色階的行為有明顯差異：

#### 1. HCT：內建強制色域搜索（自動截斷）

- **機制**：HCT 的生成器（`material-color-utilities`）在產生每一步 Tone 時，會**自動在目標色域（如 sRGB）內搜尋該 Tone 能允許的最大彩度**。
- **色階表現**：
  - 當你產生 $T=95$ 或 $T=10$ 時，HCT 會自動將彩度平滑收斂至極低，產出非常乾淨、帶有淡微色調的「表面容器色（Surface Container）」與「極深文字色」。
  - 整條色階會呈現一條平滑的「紡錘形」彩度曲線。

#### 2. OKLCH：開放廣色域（需搭配色相彩度曲線）

- **機制**：OKLCH 是純數學空間，**理論上沒有色域邊界上限**（支援 P3、Rec.2020 等廣色域）。
- **色階表現**：
  - 如果你只是單純用數學在 CSS 裡做 `oklch(calc(l + 10%) c h)`（固定 $C$ 只變 $L$），在極高與極低明度時會產生「超出螢幕色域」的顏色，必須依賴瀏覽器的色域映射（Gamut Mapping）處理。
  - 因此，像 **Tailwind CSS v4** 這種以 OKLCH 建立的專業色階表，通常會手動或透過貝茲曲線（Bezier Curve）**為不同階層客製化微調 $C$ 值**（讓 500 階彩度最高，50 階與 950 階彩度自然收斂歸零）。

---

### 三、 程式實作與 Web 生態支援度（最大實務差別）

這是兩者在工程落地時**最大的分水嶺**：

```
┌─────────────────────────────────────────────────────────────┐
│ OKLCH: 瀏覽器原生支援 (Native CSS)                          │
│ 零依賴、純 CSS 即時計算、支援相對色彩語法 (RCS)             │
└─────────────────────────────────────────────────────────────┘
                               ▲
                              對比
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ HCT: 非 Web 標準 (Google 自研演算法)                        │
│ 必須引入 JavaScript 函式庫，將 HCT 轉譯成 Hex / sRGB / P3     │
└─────────────────────────────────────────────────────────────┘
```

1. **OKLCH（純 CSS 就能動態算）**：
   - 現代瀏覽器（Chrome, Safari, Firefox）已**全面內建原生支援**。
   - 你可以使用 CSS Relative Color Syntax，直接在樣式表中產出色階：
     ```css
     :root {
       --primary: oklch(0.6 0.18 250);
       /* 純 CSS 就能直接算懸停色階與背景色階，不需任何 JS 套件 */
       --primary-light: oklch(from var(--primary) 0.95 calc(c * 0.2) h);
       --primary-dark: oklch(from var(--primary) 0.35 c h);
     }
     ```

2. **HCT（必須跑 JS 套件）**：
   - CSS 原生沒有 `hct()` 函式。
   - 你必須在前端載入 Google 的 `@material/material-color-utilities`（或在後端/打包時用 Node.js 計算），先算出每階顏色的 Hex 或 RGB 碼，再填入 CSS 變數中。

---

### 四、 生成色階的視覺氛圍總結

- **HCT 產生的色階表**：
  - **視覺風格**：帶有強烈的 **Google Material Design 3 質感**。極淺階（90\~95）非常適合作為卡片與面板背景，極深階（10\~20）非常沉穩。
  - **最大優點**：階與階之間的**明度步進極其機械化精準**，完全不用擔心文字放上去會看不清楚。
- **OKLCH 產生的色階表（如 Tailwind CSS v4）**：
  - **視覺風格**：**現代、通透、鮮明**。在廣色域（Display P3 / OLED 螢幕）上能釋放出比傳統 sRGB 更飽和純淨的高光與中間色調，且在藍紫過渡區間**完全沒有色偏**。
  - **最大優點**：與網頁標準完美融合，輕量、效能極高，適合打造靈活的 Web 設計系統。

- 如果你的專案是 **Android App**、或極度要求**嚴格遵守 WCAG 2.1 AA/AAA 規範**的企業級後台系統 $\rightarrow$ **選用 HCT**。
